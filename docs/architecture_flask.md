# Архитектура версии Flask

Приложение формирует HTML на сервере с помощью Flask и Jinja2. Данные хранятся
в SQLite. Общая структура показана в [описании архитектуры](architecture.md),
зависимости модулей на [схеме компонентов](diagrams/components.svg).

## Создание и запуск приложения

Фабрика `create_app(db_path=None, secret_key=None)` находится
в `src/infosec_desk/web.py`. Она определяет путь базы, вызывает `initialize`,
создаёт объект Flask и регистрирует маршруты, обработчик HTTP-ошибок
и заголовки ответов. HTML-шаблоны получают подготовленные данные через `show`.

| Точка входа | Поведение |
| --- | --- |
| `python run.py` | Подготовка Python-окружения и запуск команды `serve` |
| `python -m infosec_desk` | Команды приложения из `__main__.py` |
| `wsgi:app` | Объект Flask для Gunicorn; используется конфигурациями Render и Docker |

Локальный адрес по умолчанию: `127.0.0.1:8000`. Путь базы, адрес и порт
задаются аргументами `--db`, `--host`, `--port` либо переменными
`INFOSEC_DB_PATH`, `INFOSEC_HOST`, `INFOSEC_PORT`.

WSGI-вход требует `INFOSEC_SECRET_KEY` длиной не менее 32 символов
и `INFOSEC_DEMO_PASSWORD` длиной не менее 14 символов. При первом запуске он
копирует учебную базу в отдельный рабочий файл; затем задаёт пароли трёх
демонстрационных пользователей из переменной окружения. При повторном запуске
используется существующий рабочий файл. Подробные команды приведены
в [руководстве по размещению](deployment_render.md).

## Сеанс и проверка доступа

Flask хранит подписанный сеанс в cookie. В сеансе находятся идентификатор
пользователя, CSRF-токен и сообщения для следующей страницы. Текущий пользователь
загружается из базы по `user_id`. Функция `require_user` проверяет вход и роль;
права на конкретную заявку дополнительно проверяются предметными функциями.

Cookie имеет параметры `HttpOnly` и `SameSite=Lax`. Переменная
`INFOSEC_SECURE_COOKIES=1` включает `Secure`; этот параметр задан в `render.yaml`.
Секрет сеанса берётся из аргумента фабрики, `INFOSEC_SECRET_KEY` либо генерируется
при создании приложения. Постоянный ключ сохраняет действительность сеансов
между перезапусками сервера.

Формы изменения данных проходят проверку `secure_form`: токен формы сравнивается
с токеном сеанса. Гость при обращении к закрытому разделу получает перенаправление
303 на `/login`; недостаточные права и неверный CSRF дают ответ 403.
Доступ к файлу-вложению определяется доступом к его заявке.
[Матрица маршрутов](route_matrix.md) содержит права каждой операции.

## Обработка заявки

1. `GET /tickets/new` проверяет вход и показывает форму.
2. `POST /tickets` проверяет сеанс и CSRF, затем вызывает `service.create_ticket`.
3. Предметная функция проверяет поля, категорию, приоритет и выбранное СЗИ.
4. Транзакция сохраняет заявку, событие регистрации и первоначальный статус.
5. Обработчик отвечает перенаправлением 303 на карточку созданной заявки.

При изменении заявки `POST /tickets/<id>/update` допускает специалиста
и администратора. `service.update_ticket` проверяет переход по `TRANSITIONS`
и назначение активного специалиста или администратора. Изменения сохраняются
в журнале, а смена статуса также в `ticket_status_history`.

Комментарии и вложения обрабатываются отдельными маршрутами. Шаблоны показывают
переданные им данные; SQL-запросы выполняются в Python-модулях.

## Хранение и обмен

`db.py` задаёт схему, включает внешние ключи на каждом подключении
и предоставляет транзакции с `BEGIN IMMEDIATE`, фиксацией или откатом.
`initialize` создаёт таблицы и дополняет существующие базы полями `assets.active`
и `tickets.resolved_at`. Все 11 таблиц показаны на
[полной схеме базы](diagrams/database_11.svg).

`service.py` выполняет предметные операции. Маршруты также читают SQLite
для отображения и выгрузки данных. CSV/XLSX-экспорт заявок и JSON-экспорт СЗИ
реализованы в `web.py`; JSON-импорт СЗИ выполняет `exchange.py`.
Команды импорта и экспорта доступны также через `__main__.py`.
`maintenance.py` предоставляет резервирование базы и проверку манифеста версии.
